## Scope and design

The new suite has its own `playwright.frontend.config.ts`. It uses two workers with independent browser contexts, a fixed dedicated loopback server, no retries and no arbitrary server reuse. The server launcher serves the production standalone build and its public/static assets in one owned process. SIGTERM is configured for teardown. Reports live at repository-root `output/playwright/`, outside the frontend source lint traversal.

Only `GET /api/auth/methods` is stubbed. Global `AuthProvider` also requests `GET /api/user/profile`; the fixture aborts that request and records the missing backend dependency without inventing authentication state. Any other API request is aborted and fails the case. The only console exclusion is the matching profile URL with `ERR_BLOCKED_BY_CLIENT`; other console errors and all page errors remain failures. No success response for registration, sign-in or reset is simulated.

Application changes are limited to eight input test IDs in three anonymous forms. Branding, layout, translations and behavior are unchanged. Existing authenticated test files were neither deleted nor rewritten to appear passing. The original config now refuses to reuse an arbitrary running server and excludes the separately configured frontend-only directory.

The fixture consumes O(events) memory per case for browser audit data, bounded by the short scenario and timeout; selectors and route construction have fixed cost. Context isolation avoids shared account/session state, while two workers bound browser CPU/memory. The page matrix grows linearly with pages and project configurations. There is no new application runtime algorithm, request or dependency.

Boundary cases encoded include empty and malformed fields, a reset route missing its address, URL-encoded email, digit filtering, mismatched passwords, retained locale during navigation, keyboard state changes, delayed method discovery and the all-disabled state. Real auth state, backend concurrency, recovery-token consumption and the blocked security-review candidates are outside this batch. No exhaustive accessibility or authentication claim is made.
